# Plano de migração: `workspaces/angular` (Angular 21) → `workspaces/angular-22` (Angular 22)

> Rascunho para execução. Segue o mesmo método da migração anterior (Angular 20 → 21, documentada em `docs/plano-migracao-angular-21.md`): geração 100% via Angular CLI, conteúdo portado do workspace atual pro esqueleto novo, nada escrito à mão que o CLI já escafolda. Diferença em relação à vez passada: não há gambiarra estrutural pra corrigir (`utils/` já é lib de verdade, containers já seguem a convenção `*-container`/`*-component`, zoneless e SSR já são o padrão) — o trabalho aqui é (a) trocar a casca do workspace pra versão nova e (b) adotar os padrões que o próprio Angular 22 tornou default/recomendado.

## 1. Objetivo

Recriar as duas aplicações (`boilerplate-user`, `boilerplate-administrator`) e as bibliotecas `@bruno-bombonate/*` + `boilerplate-utils` dentro de `workspaces/angular-22`, sempre via `ng generate`, portando o conteúdo de `workspaces/angular` (Angular 21) 1:1, exceto pelos três ajustes de convenção decididos na seção 3.

`workspaces/angular` continua rodando normalmente até a migração ser validada — só como referência de código a portar, sem alterações.

## 2. Estado atual (levantamento)

- `workspaces/angular-22` existe, gerado via `ng new` (Angular CLI 22.1.8 / Angular 22.1.7), `angular.json` sem nenhum `project` registrado — partimos do zero, igual da vez passada.
- `workspaces/angular` está no estado que a migração anterior deixou: zoneless por padrão (sem `provideZonelessChangeDetection()` explícito), SSR obrigatório nas duas apps, `boilerplate-utils` como lib real (`@app/boilerplate-utils`), as 5 libs `ngx-*` publicadas em `21.0.0`/compat `21.x`, `OnPush` explícito em todo componente, convenção de container/rotas já formalizada (`<nome-base>-container.ts` + `<nome-base>-routes.ts`, via `--path=.../containers/<nome-base> --flat`).
- O `AGENTS.md` gerado pelo `ng new` do Angular 22 (`workspaces/angular-22/AGENTS.md`) já aponta as diferenças de convenção relevantes frente ao `AGENTS.md` atual (`workspaces/angular/AGENTS.md`):
  - **`OnPush` agora é o padrão** — a recomendação nova é **não** declarar `changeDetection: ChangeDetectionStrategy.OnPush` explicitamente.
  - `model()` para propriedades two-way bound, no lugar de um par manual `input()`/`output()`.
  - `linkedSignal()` para estado derivado de múltiplas fontes reativas que precisa ficar sincronizado.
  - **Signal Forms (`@angular/forms/signals`) estável a partir do v22**, indicado como forma preferida para formulários novos.
  - **`@Service` decorator** como alternativa a `@Injectable({ providedIn: 'root' })` para singletons.
  - Reforço explícito de não importar `CommonModule` — já era seguido de fato no workspace atual (conferido via grep: zero ocorrências de `import ... CommonModule` em `projects/`), não é mudança real de código, só formalização.
- Confirmado via `require('@angular/forms/package.json').exports` que o pacote instalado em `angular-22` realmente expõe `./signals` e `./signals/compat` (não é só anúncio de release notes) — o `.../compat` é o caminho de interop entre Signal Forms e Reactive Forms, relevante pra decisão 3.2.
- Testado com `--dry-run`/geração real num scratch isolado (Angular CLI 22.1.8): as convenções de geração da migração anterior continuam **idênticas**:
  - `ng generate component application-container --path=projects/.../containers/application --flat` → `containers/application/application-container.ts`, sem aninhamento extra — mesmo resultado documentado na seção 3.2 do plano 21.
  - `ng generate guard application-container` → `application-container-guard.ts` (sufixo automático, sem opção de desligar) — igual ao v21.
  - `ng generate service user-service` → `user-service.ts` (sem sufixo automático) — igual ao v21.
  - Componente gerado pelo CLI **não** inclui mais `changeDetection: ChangeDetectionStrategy.OnPush` no decorator (confirma a mudança de default).

## 3. Decisões tomadas nesta conversa

### 3.1 `OnPush` deixa de ser explícito
A partir desta migração, nenhum componente porta ou ganha a linha `changeDetection: ChangeDetectionStrategy.OnPush` — segue o novo default do Angular 22. Isso é o inverso da decisão equivalente na migração 20→21 (lá, zoneless virou automático mas `OnPush` foi mantido explícito por decisão sua). Ajuste a aplicar: remover a linha do decorator em todo componente portado.

### 3.2 Signal Forms: suporte duplo em `ngx-classes`/`ngx-forms`, não substituição
Decisão sua: **não** é uma migração completa das duas apps de Reactive Forms para Signal Forms nesta rodada — é fazer as duas libs públicas saberem lidar com os dois modelos, já que outras aplicações suas que dependem delas podem continuar em Reactive Forms por um bom tempo.

- **`ngx-classes` (`FormComponentClass`)**: investigar na Fase 3, olhando a API real de `@angular/forms/signals`, se dá pra ter uma única classe que sirva pros dois casos (Reactive `FormGroup`/`AbstractControl` e Signal Forms `Field`/`FieldState`) ou se as diferenças de shape exigem uma `SignalFormComponentClass` irmã, com a mesma superfície pública (inputs/outputs/métodos protegidos) que `FormComponentClass` já expõe hoje. Não decidir de antemão qual dos dois caminhos — é investigação de API, não convenção de nomenclatura.
- **`ngx-forms` (`<control-error>`)**: hoje recebe `[control]="AbstractControl"`. Precisa também aceitar o equivalente em Signal Forms e decidir sozinho, em runtime, qual dos dois casos está recebendo (por shape/tipo, ou por dois inputs distintos — a definir na Fase 3 depois de mapear a API) — sem duplicar o componente em duas versões públicas.
- Ambas as libs sobem de major (mudança de API pública real). Proposta, seguindo o mesmo raciocínio usado na migração 21 (nenhuma versão 22.x publicada ainda, sem motivo pra carregar histórico de patch incremental): colapsar direto para `22.0.0` quando a Fase 3 fechar.
- Isso é a peça mais arriscada/incerta do plano — as sub-decisões de forma final (nomes de tipo, shape do input duplo) ficam para dentro da Fase 3, depois de ler o código-fonte/typings de `@angular/forms/signals`, não dá pra fechar 100% sem isso.

### 3.3 `@Service` decorator adotado
Todo service singleton novo ou portado passa a usar `@Service()` no lugar de `@Injectable({ providedIn: 'root' })`, seguindo a recomendação nova do Angular 22. Vale para `boilerplate-utils` (`UserService`, `HttpService`, `LoadingService`) e qualquer service dentro das libs `ngx-*`.

## 7. Observações / pontos em aberto

- **Fase 3 concluída — as 5 libs `@bruno-bombonate/*`.** Recriadas via `ng generate library`, conteúdo portado, todas em `22.0.0`, `ng build`/`ng test` passando (10 arquivos/20 testes em `ngx-classes`, 3/8 em `ngx-forms`, 2/2, 1/1, 1/1 nas outras três). `@Service()` adotado em todo service singleton portado (`ToastService`, `SeoService`, `AuthenticationService`, `FormsService`), `OnPush` removido de todo componente. `rxjs` entrou como peer dependency de `ngx-forms` (usado direto em `ControlErrorComponent`, gap que já existia desde a auditoria da migração 21 e passou batido).
  - **Mapeamento da API de `@angular/forms/signals`** (via os `.d.ts`/`.mjs` do pacote instalado, não documentação): `FieldTree<T>` é uma função "marcada" (`typeof valor === 'function' && valor[FIELD_TREE] === true`, exportado como `isFieldTree()`) que, chamada, retorna um `FieldState` com `value`/`touched`/`dirty`/`errors`/`valid`/`invalid` como **signals de verdade** (ao contrário do `AbstractControl` do Reactive Forms, que muta `.errors`/`.touched` imperativamente sem trocar de referência — por isso o `ControlErrorComponent` precisava do hack `toObservable(control).pipe(switchMap(c => c.events))`). Cada erro é um objeto `{ kind, message?, ... }` (`kind` como `'required'`, `'min'`, `'minLength'` — note `minLength`/`maxLength` em camelCase, diferente do `minlength`/`maxlength` do Reactive Forms, e sem `requiredTrue` separado). Signal Forms **não** aplica classes `ng-invalid`/`ng-touched`/etc. por padrão (diferença real de comportamento frente ao Reactive Forms) — só via `provideSignalFormsConfig({ classes: {...} })`.
  - **`ngx-forms` — `ControlErrorComponent` com suporte duplo.** Decisão de design: manter um único input `[control]` (sem renomear, sem quebrar uso existente em Reactive Forms), tipado `AbstractControl | FieldTree<any>`, discriminado em runtime via `isFieldTree()` (mais simples que dois inputs separados, e o discriminador já vem pronto do próprio pacote). `FormsService` ganhou `fieldErrors`/`fieldErrorVisible` (novos, paralelos a `controlErrors`/`controlErrorVisible`), com constantes default (`FIELD_ERRORS`/`FIELD_ERROR_VISIBLE`) cobrindo os validators nativos do Signal Forms. `provideNgxForms()` agora aceita ser chamado sem argumentos (antes exigia o objeto de config) e **sempre** registra `provideSignalFormsConfig({ classes: {...} })` para as 6 classes `ng-valid`/`ng-invalid`/`ng-touched`/`ng-untouched`/`ng-dirty`/`ng-pristine` — necessário para o próximo item funcionar.
  - **`ngx-classes` — não foi viável uma única classe para os dois tipos de formulário.** Confirmado: o modelo é estruturalmente diferente demais (`FormGroup` é passado pronto de fora via `input()`; um `FieldTree` normalmente nasce dentro do próprio componente via `signal()` + `form()`, então não faz sentido como `input()`). Criada `SignalFormComponentClass<TModel>` irmã de `FormComponentClass`, com a mesma superfície pública (`formData`/`formLoading`/`formReset` inputs, `formBack`/`formChange`/`formSubmit` outputs, `handleNgSubmit()`), mas `model`/`field` são propriedades `abstract` que a subclasse concreta declara (em vez de inputs). Achados de implementação:
    - `formData` → `model` precisou de um guard equivalente ao `{ emitEvent: false }` do Reactive: como `model.set()` não tem essa opção, o filtro usado foi `field().dirty()` — atualizações vindas de `formData` usam `.set()` direto e nunca sujam (`dirty`) o field; só edição via UI (ligada pelo `Field`/`[control]` do próprio Angular) suja, então `addFormValueChangesListener` só emite `formChange` quando `dirty() === true`. Mais idiomático ao Signal Forms do que replicar o mecanismo antigo.
    - `formReset` precisou capturar o valor inicial do `model` em `ngOnInit` (não dá para capturar no field initializer da classe base — `model`/`field` são abstratos, só existem depois do `super()` da subclasse concreta rodar) para poder restaurar o valor, já que `field.reset()` do Signal Forms só reseta `touched`/`dirty`, não o valor.
    - `handleNgSubmit` depende de `.ng-invalid` existir no DOM para o scroll-to-invalid funcionar — daí a mudança em `provideNgxForms()` acima ser pré-requisito documentado no README.
  - Testado com specs reais (não só "should create"): `ControlErrorComponent` tem um `describe` para cada tipo de form, exercitando `markAsTouched()`/visibilidade/mensagem de erro nos dois casos; `SignalFormComponentClass` tem um teste de submit inválido (não emite, marca touched) e válido (emite valor mapeado) usando uma subclasse de teste real com `form()`/`required()`. Todos passando.
