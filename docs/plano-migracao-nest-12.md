# Plano de migração: `workspaces/nest` (Nest 9) → `workspaces/nest-12` (Nest 12)

> **✅ MIGRAÇÃO CONCLUÍDA — corte final feito.** A pasta antiga `workspaces/nest` (Nest 9) foi removida, e `workspaces/nest-12` foi renomeada pra `workspaces/nest` — esse nome agora é o Nest 12. `package.json` (`"name"`) e `.gitignore` (voltou a versionar `.env`, igual ao v9 — decisão do corte final, ver seção 7) ajustados nesse mesmo passo. Todo o texto abaixo é o histórico real de como a migração aconteceu (decisões, achados, bugs corrigidos) — mantido como está, sem reescrever as referências a "`workspaces/nest-12`" pra "`workspaces/nest`", já que é um registro do que foi decidido e quando. A partir de agora, qualquer trabalho novo no backend Nest acontece direto em `workspaces/nest`; este arquivo continua existindo só como log/referência.
>
> Segue o mesmo procedimento adotado na migração do Angular (ver [`docs/plano-migracao-angular-21.md`](./plano-migracao-angular-21.md)): as duas aplicações e as duas libs foram recriadas do zero via Nest CLI (`nest generate`), e o conteúdo (lógica de controllers/services/entities) foi portado do `workspaces/nest` original pra dentro do esqueleto gerado — nunca o inverso.

## 1. Objetivo

Recriar as duas aplicações (`boilerplate-user`, `boilerplate-administrator`) e as duas libs (`boilerplate-database`, `boilerplate-email`) dentro de `workspaces/nest-12`, **sempre via Nest CLI**: apps via `nest generate app`, libs via `nest generate library`, e todo controller/service/module/guard/pipe/classe (DTO, entity, subscriber, strategy) via o schematic correspondente sempre que ele existir — replicando a estrutura monorepo (`apps/` + `libs/`) que já existe hoje, mas em cima da base Nest 12 gerada pelo CLI.

## 2. Estado atual (o que o levantamento mostrou)

- `workspaces/nest-12` é o output cru de `nest new` em Nest 12: projeto "standard" (não monorepo ainda), `@nestjs/core@^12.0.1`, TypeScript com `module: nodenext` (ESM, `"type": "module"` no `package.json`), `strict: true`, testes em **Vitest** (não Jest), lint via **oxlint** (não ESLint). Nenhum app/lib registrado.
- `workspaces/nest` (v9) já é monorepo (`nest-cli.json` com `"monorepo": true`): dois apps (`apps/boilerplate-user`, `apps/boilerplate-administrator`) e duas libs (`libs/boilerplate-database`, `libs/boilerplate-email`), 100% CommonJS, TypeScript com `strictNullChecks`/`noImplicitAny` desligados, testes em Jest, lint em ESLint, build via `webpack: true` no `nest-cli.json`.
- Cada app v9 tem: `main.ts` (carrega env via `require('custom-env').env(...)`, monta Swagger em `/swagger`, `enableCors()`), um único módulo raiz (`<app>.module.ts`) que só importa `BoilerplateDatabaseModule` + `BoilerplateEmailModule` + os feature modules — sem controller/service próprio no root —, e módulos de feature sob `src/modules/<domínio>` com controller + service (+ service auxiliar de reset de senha) + DTOs. Guard/strategy de JWT e (só no administrator) um `BooleanPipe` ficam em `src/utils/{guards,strategies,pipes}`.
- `boilerplate-database`: módulo central que registra `ConfigModule.forRoot({ load: [configuration] })` + `TypeOrmModule.forRootAsync(...)` lendo `config/configuration.ts` (usa `mysql2`, lista as 4 entidades manualmente), e dois módulos de domínio (`administrators`, `users`) cada um com entity + entity de reset-password + `EntitySubscriberInterface` (hash de senha com `bcryptjs`, timestamps) — sem controller/service próprio, só entities/subscribers.
- `boilerplate-email`: `MailerModule.forRootAsync` com adapter EJS (`@nestjs-modules/mailer/dist/adapters/ejs.adapter`, import profundo), templates em `src/templates/**/*.ejs`, um único `BoilerplateEmailService` com `sendResetPasswordEmail(...)`.
- Autenticação: `passport-jwt` com secret/expiração por app via env (`APP_BOILERPLATE_{USER,ADMINISTRATOR}_API_SECRET_KEY`/`_EXPIRES_IN`) — token de um app não serve para o outro, mesmo padrão do lado Angular.
- **Achado de versões (checado no npm registry hoje):**
  - `@nestjs/typeorm@12.0.1`, `@nestjs/config@12.0.0`, `@nestjs/jwt@12.0.2`, `@nestjs/passport@12.0.0`, `@nestjs/swagger@12.0.1` — todos com release compatível com Nest 12.
  - **TypeORM lançou uma major nova**: `latest` no npm hoje é `1.1.1`; a série que o projeto usa (`0.3.x`) segue mantida só na tag `legacy` (`0.3.31`). `@nestjs/typeorm@12.0.1` aceita as duas como peer (`typeorm: ^0.3.0 || ^1.0.0-dev`).
  - `@nestjs-modules/mailer` subiu de `1.8.1` (usado hoje) para `2.3.7` — duas majors de diferença. O import profundo hoje usado (`@nestjs-modules/mailer/dist/adapters/ejs.adapter`) precisa ser reconferido nessa versão (estrutura de pastas do pacote pode ter mudado), e o pacote passou a listar várias peer deps de outras template engines (`pug`, `handlebars`, `mjml`, `nunjucks`, `bullmq`, etc.) — a esperar que sejam peers opcionais (só precisamos de `ejs`), mas fica como item a validar na Fase 5, não é uma decisão de arquitetura.
- **Achado de comportamento da CLI (testado com `--dry-run` numa cópia descartável de `nest-12`, mesmo espírito da tabela de schematics testada no Angular):**
  - `nest generate app <nome>` (alias `sub-app`), na **primeira** vez que roda num projeto "standard", sempre converte o projeto pra monorepo E cria de brinde um app "sobra" usando o nome atual do `package.json` (testado: gerou `apps/nest-12` com `app.controller.ts`/`app.service.ts`/`app.module.ts` genéricos, além do app pedido). Isso bate com o que deve ter acontecido originalmente no v9: não existe hoje nenhuma pasta `apps/nest` sobrando, então esse app "de conversão" foi gerado e depois apagado manualmente. Vamos repetir o mesmo passo aqui.
  - Rodar `nest g app boilerplate-user` primeiro, aceitando a sobra (`apps/nest-12`), depois `nest g app boilerplate-administrator` (que já não gera mais sobra, workspace já é monorepo) reproduz exatamente a mesma estrutura de nomes que existe hoje (`boilerplate-user.module.ts`, `boilerplate-user.controller.ts`, `boilerplate-user.service.ts`, etc., com sufixo certo).
  - Cada app gerado por `nest g app` vem com um controller/service próprios no root (ex.: `boilerplate-user.controller.ts`) que **não existem** no v9 (lá só sobrevive o `.module.ts` — toda lógica mora em `modules/<domínio>`). Apagar esses 2 arquivos (+ spec) de cada app depois de gerar é parte do padrão, não uma alteração nova.
  - `controller`/`service`/`module`/`guard`/`pipe`: sufixo **sempre automático** (não escrever no nome) e cada um deles **atualiza sozinho o `.module.ts` mais próximo na árvore** — por isso a ordem importa: gerar sempre `nest g module modules/<domínio>` **antes** de `nest g controller`/`nest g service` no mesmo caminho, senão o CLI registra o controller/service no module errado (o mais próximo já existente, tipicamente o module raiz do app). Testado e confirmado: gerando module → controller → service nessa ordem, o `UsersModule` fica com `controllers`/`providers` certos e é o módulo raiz que importa `UsersModule` (não `UsersController` direto).
  - `class` (usado para DTOs, entities, subscribers, strategies — nenhum desses tem schematic dedicado) **não** aplica sufixo automático: o nome tem que já vir com o sufixo desejado (`nest g class modules/users/dto/user-sign-up.dto --flat --no-spec` → `user-sign-up.dto.ts`; sem o `.dto` no nome, sai só `user-sign-up.ts`). Mesma regra já documentada no Angular para `component`/`service`/`class`.
  - **`nest generate library` exige um prompt interativo de "prefix"** (novidade do Nest 12 — a versão anterior do schematic não tinha esse campo obrigatório). Confirmado por teste: não existe flag `--prefix` na CLI (`generate.command.js` não registra essa opção, mesmo o schema do schematic exigindo `prefix` como campo obrigatório), e configurar `defaultLibraryPrefix` no `nest-cli.json` **não** contorna a validação — ela roda antes do fallback ser aplicado. **Isso significa que `nest g library boilerplate-database`/`boilerplate-email` precisam ser rodados por você mesmo, direto no terminal (não por mim via ferramenta), respondendo `@app` no prompt** (é o default sugerido e é exatamente o prefixo que o projeto já usa hoje, `@app/boilerplate-database`/`@app/boilerplate-email`).
  - Os schematics já geram os arquivos com `import ... from './x.js'` (extensão `.js` nos imports relativos), coerente com o `module: nodenext` do ESM — não precisamos adicionar isso manualmente, o CLI já cobre para tudo que ele gerar.

## 3. Decisões (resolvidas com você)

| # | Tema | Decisão |
|---|---|---|
| 1 | Sistema de módulos | **ESM**, aceitando o default gerado pelo `nest new`/`nest g app` (`type: module`, `module: nodenext`). Implica reescrever `require('custom-env').env(...)` do `main.ts` para `import`, e qualquer outro `require()`/`__dirname` do código v9 para equivalente ESM (`import.meta.url`, etc., onde existir). |
| 2 | `strict` do TypeScript | **Manter `strict: true`** (default gerado). Os pontos hoje frouxos no v9 (`any` implícito, `null`/`undefined` não checado — bem presentes nos controllers, que retornam/recebem `any` em vários lugares) serão corrigidos de verdade durante a portagem, sem suprimir erro — mesmo espírito das correções de bug feitas durante a migração do Angular. |
| 3 | Test runner / lint | **Vitest + oxlint**, aceitando o default gerado — mesma escolha já tomada no `workspaces/angular` (Angular 21 também usa Vitest). Os `.spec.ts` existentes (Jest) precisam ser portados para sintaxe Vitest (majoritariamente compatível, mas `jest.fn()`/`jest.mock` viram `vi.fn()`/`vi.mock`). |
| 4 | Versão do TypeORM | **1.x** (a major mais nova, hoje `1.1.1` no npm) em vez de manter `0.3.x`. Como é uma major recém-lançada, cada entity/subscriber/query precisa ser revalidado na prática (decorators, `EntitySubscriberInterface`, `QueryBuilder`, comportamento do `DataSource`) — isso vira item explícito de validação nas Fases 4 e 8, não presumido como drop-in. |

- **Bug encontrado e corrigido — `nest g library` corrompe o script `test:e2e`.** O schematic de library faz um replace ingênuo do path-base de teste (`test/`) dentro dos *scripts* do `package.json` para "arrumar" o `test:e2e`, mas o replace é feito por substring, sem checar limite de palavra — e `vitest` contém `test` como substring (`vi` + `test`). Resultado: `"vitest run --config ..."` virou `"viapps/nest-12/test run --config ..."`. Corrigido de volta para `"vitest run --config ./vitest.config.e2e.ts"`.
